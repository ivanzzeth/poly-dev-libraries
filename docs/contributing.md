# 收录与维护

## 收录组件

1. 确认它是可复用开发库，目标仓库公开可访问；私有组件不写入本公开聚合目录。
2. 核对实际语言、用途、包路径、源提交与许可证文件。公开可见不等于许可证已确认；缺少许可信息时在目录保留明确状态，不能套用本仓库 MIT。
3. 选择 `语言/领域/库` 路径；保留组件原仓库名和包路径，必要时目录可用易读别名。
4. 运行 `git submodule add --name <组件名> https://github.com/<owner>/<repo>.git <路径>`，切换到经过核对的具体提交并暂存 gitlink；不配置自动跟踪分支。
5. 更新 `libraries.json`，执行 `make catalog`、`make check` 和 `make check-checkouts`。
6. 记录组件测试与发布状态。目录检查通过只证明聚合一致性，不能据此声明该 SDK 或库已经生产验收。

## 更新组件

先在组件自己的仓库提交并推送，再更新聚合 gitlink。提交说明包含旧／新版本、行为差异、依赖与迁移影响及相应测试证据。
禁止把未推送的本地组件提交登记为可复现公开版本。CI 通过匿名递归 checkout 验证所有固定提交可获取。
不要使用 `git submodule update --remote` 无差别升级所有组件；新旧组件的包依赖关系应在各自 CI 中验证。

## 应用迁移

新项目直接依赖已交付组件，尚未交付的公共机制优先在所属组件库补齐；采用其能力前必须完成真实集成验收。
老项目每次迁移一个组件或完整流程：固定原行为、增加特征测试、替换依赖、验证失败恢复、独立发布。
源码目录重组不等于应用运行时已经迁移，也不要求同步更新应用 `go.mod`。
业务规则、消息载荷、业务幂等与外部协议适配留在应用侧；通用执行机制、后端实现与跨项目测试放在组件库。

## 工程规范

组件自行维护版本锁、代码生成输入、负向与故障恢复测试、发布说明。可复用的 CI 和生成配置后续集中维护，引用须固定版本。
本聚合 CI 只运行自己的目录校验，不执行未经明确配置的子模块构建脚本，不需要账户密钥或生产环境。
更新清单和文档使用 Python 3 标准库工具；目录由 `libraries.json` 生成，gitlink 是源码提交的权威，避免第二份 SHA 清单漂移。
