# 架构与边界

状态：聚合结构已建立；公共组件新增能力按各自仓库交付。

## 三层组织

1. `poly-dev-libraries` 管理分类、源码组合、共享规范与导航。
2. 各语言下的库通过独立 Git 仓库和子模块维护。仓库按内聚职责与发布需求划分，不按每个模式、类型或函数划分。
3. 库内 package 提供具体组件。例如 containers 已有 queue、state、pubsub、locker，计划新增 outbox；后续模式是否收录先判断职责是否相符。

Go 优先建立实际使用链路。其他语言按具体项目需求新增实现，不先建立没有消费者的空仓库。
公共库不得反向依赖某个业务项目；业务通过适配器提供处理函数、上下文、事务、配置或监控接口。

## 代码共享与运行隔离

公共组件作为应用依赖运行，各服务继续拥有自己的数据库、消息、配置和生命周期。聚合库不建立跨业务共享数据库或中央消息服务。
需持久化的组件提供版本化 schema 资源与接入说明，宿主发布流程显式执行迁移。不同组件的迁移版本空间、表名及锁标识须隔离，不在 import 或构造函数中自动改库。
已有 Queue/PubSub 适配器是否适合可靠投递，须核对持久性、确认、重放和背压能力；相同接口不能掩盖不同保证。

## 跨语言模式契约

`patterns/` 规定行为、失败语义、能力边界和验收场景。实现状态按语言与后端分别记录。
可执行共享测试向量随首个实现加入，各语言 runner 读取相同场景并运行真实后端；不存在 runner 或测试结果时不得标为符合规范。
规范版本、组件版本与聚合提交分别记录。应用锁定组件发布版本，聚合 gitlink 固定源码快照，两者不能互相冒充兼容认证。

## 发布与依赖

组件独立打标签、发布和运行测试；聚合仓库更新 gitlink 时评估变更、迁移与兼容影响。
根目录不创建统一 `go.mod` 或强制覆盖所有模块的 `go.work`，避免改变不同 SDK 的原有依赖选择。
仅确有联合开发需要时，在组件侧提供显式 opt-in 的工作区配置；临时本地替换不能作为可发布包的依赖方案。
CLI 或例子随库存在不影响收录；以部署服务或业务应用为主体的仓库继续独立管理。
