# Transactional Outbox

版本：草案 0.1。计划归入现有 containers 库的 `outbox` package；本文不是已交付 API 或生产保证。

## 边界

Outbox 是支持同事务追加和可靠投递的持久化消息容器。业务变更与消息在同一数据库事务内提交；数据库提交后由 worker 投递。
业务负责事件内容、产生时机、消费逻辑、幂等语义和顺序需求。库负责存储、领取、租约、投递调度、退避、死信、重放与观测接口。
不能用“数据库提交后写 Redis”替代事务追加；不承诺跨数据库原子性或网络副作用恰好一次。

## 首期接口约束

- PostgreSQL 适配器的追加操作显式接受宿主已有 `*sql.Tx`；不得自行另开事务。库不管理业务表，也不隐式提交宿主事务。
- 消息有稳定 ID、载荷版本、创建时间与受限大小；需要顺序的消息额外有明确的键和序号。载荷不自动记录到日志。
- 领取采用有界批次与租约／领取令牌；确认、重试、续租均校验当前领取令牌，过期 worker 不能改写后继任务状态。
- 投递回调执行在数据库事务之外。交付允许重复；消费者需使用稳定消息 ID 或业务操作 ID 幂等。外部副作用是否支持幂等由下游能力决定。
- 首期不宣称跨 worker 全局 FIFO。要求同键顺序的消费者必须通过已实现并验收的顺序机制或业务版本约束接入。
- 投递失败按有界策略退避；达到限制进入可观察的死信状态，可显式重放。不得把死信当成功；重放保留幂等身份。
- 启停、超时、取消、背压、批次大小和指标通过显式配置／接口提供，不引入全局单例。
- schema 随组件版本发布，由宿主显式迁移；宿主保留数据所有权。内存测试后端不冒充 PostgreSQL 事务与持久性保证。

## 最小验收场景

| ID | 场景 | 预期 |
|---|---|---|
| OB-01 | 业务与消息一起提交 | 业务写入和待投递消息同时可见 |
| OB-02 | 写消息后回滚／panic | 业务写入与消息均不可见 |
| OB-03 | 提交后、投递前进程退出 | 重启后消息仍可领取 |
| OB-04 | 投递成功、确认前进程退出 | 允许重投同一 ID；幂等消费者不重复产生效果 |
| OB-05 | 多 worker 同时领取 | 同一时刻只有有效领取权；过期后可恢复 |
| OB-06 | 旧 worker 在新租约后确认 | 旧令牌无法改变新租约状态 |
| OB-07 | 失败直至上限后重放 | 可观察地进入死信，重放保留身份与历史 |
| OB-08 | 事务冲突导致宿主回调重试 | 无回滚残留；稳定业务操作不会创建重复逻辑消息 |
| OB-09 | 上下文取消、超时或关闭 | 有界停止，不把未完成消息标记成功 |
| OB-10 | 提交结果未知 | 不声称已回滚，宿主可按操作身份查询与核对 |

真实 PostgreSQL、多进程退出与恢复测试是这些保证的必要证据。模拟实现通过不能单独标记生产后端验收。
